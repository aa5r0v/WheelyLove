# 18. Чеклисти за поддръжка

Отмятай редовно; датите в скоби са напътствия, не догма.

## 1. Всеки ден (2 мин, може от телефона)

- [ ] Сайтът отваря `https://wheelylove.net/` (и `/en`).
- [ ] Влизане като потребител → „Моите резервации“ зарежда.
- [ ] (На VPS) `docker ps --filter name=wheelylove` — двата контейнера
      `healthy/Up` повече от ден.

## 2. Всяка седмица

- [ ] Административен преглед: нови резервации отбелязани „платени“;
      отменени часове с причина.
- [ ] Разписанието има часове ≥4 седмици напред; ако не — бутона „Генерирай“
      (`/admin/schedule`) и проверка на шаблоните ([07](07-raspisanie-i-vreme.md)).
- [ ] Архивът от снощи съществува и не е празен:
      `ssh <user>@164.138.216.72 'ls -lh /srv/wheelylove/backups | tail -4'`
      ([10 §6](10-faylove-i-arhivi.md)).
- [ ] Провалени писма за седмицата:
      `bash /srv/wheelylove/deploy/scripts/check-email-failures.sh 7d; echo $?`
      (0 = чисто).
- [ ] Диск: `df -h /srv/wheelylove` — под 80%?

## 3. Всеки месец

- [ ] Пълна проверка на release-процеса в replica/локално: `npx tsc
      --noEmit`, `npm run lint`, `npm test` ([13 §8](13-testove-i-proverki.md)).
- [ ] Възстановяване на архив В ТЕСТОВА среда (не върху продукция!): разпакетирай
      нощен dump в локална база и отвори сайта срещу нея — доказва, че
      архивът реално работи.
- [ ] Ревизия на акаунти: кои потребители са admin/instructor (SQL в
      [04 §5](04-baza-dannih.md), само тестова база; за продукция —
      през тунел с`SELECT`-only сесия); махни достъпа на напуснали.
- [ ] Проверка на датите на сертификатите: `ls -l /etc/ssl/cloudflare/`
      (Cloudflare origin cert-овете са дълги, но проверявай).
- [ ] Синхрон на кода ([16 §5](16-sinhron-s-iztochnika.md)): living tag ↔
      локални комити ↔ GitHub; ако push-ът все още е 403 — сверка дали
      release-ите са отразени в комити.

## 4. Преди всеки release (винаги)

- [ ] Всичко е commit-нато; `git status --short` чист (без `src/` файлове).
- [ ] `npx tsc --noEmit` — 0 грешки.
- [ ] `npm run lint` — 0 грешки.
- [ ] `npm test` — зелено на изолирана `_test` база.
- [ ] `npm run build` — минава (в копие на дървото при вървящ dev server).
- [ ] Ръчните стъпки 1-4 от [13 §7](13-testove-i-proverki.md).
- [ ] Ако има нова миграция: обратно съвместима ли е? ([14 §4](14-deploy-i-release.md))
      триене само през deferred-механизма.
- [ ] RAM на VPS ≥ 2.8 GB свободни (`deploy.sh` сам проверява).
- [ ] Известено ли е студиото за краткото 502 прекъсване (5-20 s)?

## 5. След всеки release

- [ ] `DEPLOY OK` съобщение с нов таг; `state/tag.env` = новия ид.
- [ ] `curl -sI https://wheelylove.net/` → 200/307.
- [ ] Бърз visual check: начална, разписание, вход, една резервация в тестов
      ред (или поне gallery + sports).
- [ ] `docker logs --tail 30 wheelylove-app` без стек-трейсове.
- [ ] При проблем: `bash /srv/wheelylove/deploy/rollback.sh` ([14 §5](14-deploy-i-release.md))
      и запис на причината.

## 6. Тримесечно

- [ ] Преглед на `deploy/README.md` спрямо реалността (nginx конфиг,
      systemd таймери, cron редове — има ли drift?).
- [ ] Обновяване на зависимости (`npm outdated` локално) — само с пълен
      тестов цикъл и отделен release; никога „на живо“.
- [ ] Преглед на тази документация: бележки ⟨ЧАКАЩО⟩, които вече са пуснати —
      обнови ги (координаторът потвърждава).
- [ ] Проверка на потребителите с достъп до VPS (кой има ключ/роля;
      [17](17-vps-dostap-adelina.md)).

## 7. Годишно

- [ ] Възстановяване на ЦЕЛИЯ стек от архиви върху чиста машина (тест) —
      единственото истинско доказателство за плана за възстановяване
      (install.sh → restore dump → restore uploads → DNS тест).
- [ ] Ротация на секретите: `POSTGRES_PASSWORD`, `CRON_SECRET` (при
      подозрение — и `BETTER_AUTH_SECRET`; изважда всички от вход — вж.
      [11 §3](11-env-promenlivi.md)).
- [ ] Архиви навън от сървъра: работи ли външното копие ([10 §4](10-faylove-i-arhivi.md))?
