## 1. Какво е проектът (30 секунди)

собствен auth (Better Auth в собствен Postgres 17), два езика (bg по
подразбиране, en под `/en`), Docker на VPS зад Cloudflare+nginx. Локално
репо: `D:\dev\Wheelylove`, клон `feat/instructor-panel`. Продукция:
`https://wheelylove.net` (VPS 164.138.216.72, `/srv/wheelylove`).

## 2. Непоклатни правила

1. **Промени само в локалното репо.** Никакви редакции на VPS файловете, на
   контейнера или `releases/`. Пътят на кода: локална промяна → тестове →
   commit → release архив → deploy (14-deploy-i-release.md).
2. **Не пипай `.env*` файлове** — не ги чети, не ги показвай, не ги
   комитвай. Документирай само имена на променливи (11-env-promenlivi.md).
3. **Тестовете върху изолирана база** (`DATABASE_URL` … името свършва на
   `_test`; порт 5432 е споделен — забранен). Пазачът в
   `src/lib/test-db-guard.ts` спира иначе.
4. **Никакви секрети/PII в логовете, документи, комити.** Имейлите в
   приложения код се маскират — следвай примера (`src/lib/email.ts:265`).
5. **VPS-ът е споделен** (QHub, OpenVPN и др.): никога `docker prune`,
   рестарт на docker/чужди контейнери, системни промени (14 §9).
6. **Плащането е само на място** — не „добавяй“ Stripe/онлайн плащане, без
   изрично ново задание. Полето `card` в enum-а е наследено от стари данни.
7. **Миграциите са обратно съвместими**; триенето на колони — само през
   `deploy/deferred-migrations/` механизма с един release пауза (14 §4).
8. **Ролята не идва от клиента никога** — само set-admin/set-instructor CLI
   или админ панел действия с проверки (06-auth-i-sigurnost.md).
9. Скриптовете `deploy.sh`/`rollback.sh` изискват root на VPS — не се
   „оправяй“ да ги пускаш другояче; ползвай handoff реда (17 §7).
10. Не комитвай работни файлове на агенти в корена (`.glm-*`, `.codex-*`)
    и `docs/research/` остава недокоснат.

## 3. Задължителен работен процес при ПРОМЯНА ПО КОДА

```bash
cd /d/dev/Wheelylove
# 1) разбери какво пипаш: главите 03-08 описват маршрутите/договора
# 2) branch
git checkout -b <кратко-име>
# 3) промяна + тест (изолирана база! виж 12 §2)
npx tsc --noEmit && npm run lint && npm test
# 4) ръчни стъпки от 13 §7, ако докосваш UI/писма
# 5) commit с описателно съобщение; после: release процесът от 14 §2
```

Ако тестът червенее: първо разбери ЗАЩО. Никога не „подравнявай“ тест, за да
мине (анти-примерите в историята на проекта са описани в коментарите на
кода). Ако не можеш да го оправиш — спри и докладвай на Аделина.

## 5. Какво НЕ трябва да правиш (често изкушение)

- Да „пооправяш“ nginx/файъруол/SSH конфигурации по VPS (само операторът).
- Да изпращаш реални имейли от локалната среда (ползвай catcher — 13 §6).
- Да тестваш срещу продукцията през SSH тунел с нещо друго освен
  read-only SELECT / set-admin скриптовете (и те — внимателно, 06 §3).
- Да комитуваш миграция, която трие колона, използвана от текущата жива
  версия (rollback става невъзможен).
- Да добавяш зависимости „за удобство“ — проекта е умишлено минимален
  (погледни списъка в 01 §2).

## 7. Речник на локациите (бърза карта)

- Бизнес логика: `src/lib/*.ts` (по една тема на файл — продължавай така).
- Страници: `src/app/[locale]/…`; API: `src/app/api/…`.
- Схема/миграции: `src/db/schema.ts`, `drizzle/`.
- Продъкшън скриптове: `deploy/` (пълният ops наръчник е `deploy/README.md`).
- CLI инструменти: `scripts/` (set-admin, set-instructor, seed*).
- Тестове: до основния файл (`bookings.ts` → `bookings.test.ts`).

## 8. Когато нещо не е описано

1. Чети кода — коментарите там са богати и обясняват „защо“, не само „какво“.
2. Проверявай твърдения срещу кода, не срещу паметта: проекта е млад и се
   движи бързо.
3. При съмнение в продукция: направи snapshot на логовете (15 §0) и питай
   оператора, вместо да експериментираш.
