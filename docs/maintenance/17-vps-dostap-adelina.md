# 17. Отделен VPS достъп за Аделина — план и чеклист

> **СТАТУС: НЕ СЪЗДАДЕН ОЩЕ.** Към 2026-10-06 Аделина НЯМА собствен SSH достъп
> до сървъра. Публичният ѝ ключ още не е получен. Тази глава е планът, по който
> достъпът да се издаде, когато ключът пристигне. Дотогава достъпът до VPS се
> осигурява от координатора/собственика.

## 1. Принципи (задължителни)

1. **Отделен именуван акаунт** (`adelina`) с отделен ключ — никога споделен
   root, никога чужд частен ключ. Частният ключ не напуска машината на
   Аделина; на сървъра се качва САМО публичната част.
2. **Малки привилегии в началото**: акаунтът се създава без sudo и без
   docker група. Разграничението е важно, защото:
   - членство в **docker групата = root** (docker ioctl-ът може да монтира
     каквото иска на хоста);
   - **пълен sudo (`ALL=(ALL:ALL) ALL`) = root**;
   - deploy скриптовете изискват root (`require_root` в
     `deploy/scripts/lib.sh:18`) — те не могат да се изпълнят „вързано“ от
   непривилегирован акаунт и това е ОК: release-ите се подписват от
   координатора (вж. §5).
3. **Никаква автоматизация по SSH/firewall**: създаването на акаунта, ключа и
   евентуалните правила е РЪЧНА стъпка от сървърния оператор по чеклиста
   (§6). Никой скрипт/agent не пипа `authorized_keys`, sshd_config или
   firewall-а.
4. Кодът се редактира **локално** (уреди чрез git + release архиви,
   [14](14-deploy-i-release.md) и [16](16-sinhron-s-iztochnika.md)); на VPS
   не се редактират нито файлове на работещия контейнер, нито release
   папките.
5. **Разделение със съдържанието на сайта**: съдържанието се управлява през
   браузъра с админския акаунт НА САЙТА (`/admin`, вж.
   [09](09-admin-rukovodstvo.md)) — за това не е нужен SSH, нито се създават
   нови идентификации от тази глава. SSH акаунтът тук е само за достъп до
   сървъра и е напълно отделен от администрирането на съдържанието.
   (Кой точно държи админския акаунт на сайта, е извън обхвата на тази
   глава; издава се по процедурата от [09 §8](09-admin-rukovodstvo.md).)

## 2. Аделина: създаване на ключ (Windows или macOS)

**Windows 10/11 (PowerShell — вграден OpenSSH):**

```powershell
# ВНИМАНИЕ: не презаписвай существуващ ключ! Първо провери:
Test-Path $env:USERPROFILE\.ssh\id_ed25519
# False -> създаване (без passphrase е удобно, но с passphrase е по-безопасно):
ssh-keygen -t ed25519 -a 100 -f $env:USERPROFILE\.ssh\id_ed25519 -C "adelina@wheelylove"
# True -> НЕ генерирай нов с това име; ползвай съществуващия или друго име
#         (id_ed25519_wheelylove) и го описи в ~/.ssh/config (§3).
```

**macOS/Linux (Terminal):**

```bash
[ -f ~/.ssh/id_ed25519 ] && echo "вече има ключ — не го презаписвай" \
  || ssh-keygen -t ed25519 -a 100 -f ~/.ssh/id_ed25519 -C "adelina@wheelylove"
```

**Какво се споделя (САМО това!):** публичният ключ:

```bash
# покажи публичната част (тя не е тайна):
cat ~/.ssh/id_ed25519.pub        # Windows: type $env:USERPROFILE\.ssh\id_ed25519.pub
```
Изпрати този ред (`ssh-ed25519 AAAA… adelina@wheelylove`) по доверен канал на
сървърния оператор. **Никога не изпращай файла без `.pub`, паролата на
ключа или частния ключ.**

## 3. SSH конфигурация на машината на Аделина

Създай/допълни `~/.ssh/config` (Windows:
`C:\Users\<ти>\.ssh\config`):

```
Host wheelylove-vps
    HostName 164.138.216.72
    User adelina
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes
    # първото свързване ще те пита за fingerprint — виж §4 преди да приемеш!
```

После влизането е просто: `ssh wheelylove-vps`.

## 4. Проверка на отпечатъка НА ОТДЕЛЕН КАНАЛ (out-of-band)

При първо свързване SSH показва fingerprint на хоста и пита `Are you sure you
want to continue connecting?`. **Не приемай сляпо** — отпечатъкът се сверява
по друг канал (обаждане/съобщение до оператора, който пуска на сървъра):

```bash
# От страната на оператора (на самия VPS):
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
# (показва: "256 SHA256:xxxx… comment")
```
Свери този `SHA256:…` с това, което показва твоят SSH при първия опит.
Съвпадат ли → приеми (`yes`). НЕ съвпадат ли → прекъсни (`no`) и уведоми
оператора (вероятен man-in-the-middle). След приемане fingerprint-ът остава
записан в `known_hosts` и повече не се пита.

## 5. Какво може да прави акаунтът в началото (least privilege)

Създаден без sudo/docker група, акаунтът `adelina` може:

- да влиза през SSH и да **чете** логовете на проекта:
  `docker logs --tail 100 wheelylove-app` работи и без група (достъп до
  docker socket-а обикновено е нужен — ако командата откажеpermission,
  операторът решава дали да даде само четене през конкретен wrapper или
  отделна процедура; това е от решението на оператора, не автоматизираме);
- да проверява състоянието:
  ```bash
  docker ps --filter name=wheelylove
  cat /srv/wheelylove/state/tag.env          # какъв release върви
  df -h /srv/wheelylove                      # диск
  ```
- да разменя release архиви в СВОЯ работен кът `/srv/wheelylove-handoff/`
  (създаден по чеклиста): качва се `scp wheelylove-<sha>.tar.gz
  wheelylove-vps:/srv/wheelylove-handoff/incoming/`, а операторът (root)
  проверява и пуска `deploy.sh`.

**Както НЕ може** (и не трябва, докато изрично не се реши друго): да пуска
`deploy.sh`/`rollback.sh` (искат root), да пипа `/srv/wheelylove/.env`, да
менеджва контейнери, да модифицира nginx/firewall.

**Развитие на правата (когато и ако се реши)** — всяка стъпка е отделно
решение на собственика, с осъзнаване какво носи:
- ограничено sudo за конкретни скриптове (`deploy.sh`/`backup.sh` като
  единични `sudoers` реда с `NOPASSWD` за точно тези путици) — дава
  самостоятелен deploy без пълен root;
- docker група — САМО при реална нужда, защото е root-еквивалент на машината
  (споделена с други услуги!);
- пълен sudo — само ако Аделина става единственият оператор на сървъра.

## 6. Чеклист за оператора (сървърен администратор) — РЪЧНО, стъпка по стъпка

Изпълнява се на VPS от root, когато публичният ключ пристигне. Нищо тук не
се автоматизира от скриптове на репото.

```bash
# 0. Предпоставки: имаш ли публичния ключ? (плейсхолдър — не реална стойност)
#    ADelina_PUB_KEY="ssh-ed25519 AAAAC3Nza... adelina@wheelylove"

# 1. Акаунт (без sudo, без групи):
useradd -m -s /bin/bash adelina
passwd -l adelina          # без парола — само с ключ

# 2. Ключ (само публичната част; файлът с 600 на директория, 644 на ключа):
install -d -m 700 -o adelina -g adelina /home/adelina/.ssh
echo '<ADelina_PUB_KEY>' > /home/adelina/.ssh/authorized_keys
chown adelina:adelina /home/adelina/.ssh/authorized_keys
chmod 600 /home/adelina/.ssh/authorized_keys

# 3. Работен кът за release handoff:
install -d -m 755 -o adelina -g adelina /srv/wheelylove-handoff/incoming

# 4. (По избор, решение на оператора) четимост на логовете без sudo:
#    НЕ се дава docker група тук. Ако docker logs отказва без група,
#    операторът избира: периодично копиране на логове в кята, или ограничен
#    sudo ред за конкретни команди. Без широки granting.

# 5. Тест ОТ машината на Аделина (тя го прави):
#    ssh wheelylove-vps 'id && cat /srv/wheelylove/state/tag.env'
```

**Не се прави в тази стъпка:** `usermod -aG docker`, редове `ALL=(ALL) ALL`
в sudoers, промени по sshd (напр. Port/PasswordAuthentication — sshd на
сървъра вече е настроен от собственика), промени по firewall. Ако някоя от
тези се наложи някой ден — това е отделно, документирано решение.

## 7. Ред при предаване на release (handoff) — как работи без root

1. Аделина качва архива: `scp /tmp/wheelylove-<sha>.tar.gz
   wheelylove-vps:/srv/wheelylove-handoff/incoming/`.
2. Уведомява оператора (който има root) — с SHA на архива:
   `sha256sum /tmp/wheelylove-<sha>.tar.gz`.
3. Операторът сверява sha256, мести архива в `/tmp/` и пуска
   `bash /srv/wheelylove/deploy/deploy.sh /tmp/wheelylove-<sha>.tar.gz`
   (14 §2). Резултатът се сверява съвместно (health + tag.env).
4. Архивът се изтрива от incoming след deploy.

Този ред държи „кой пуска код по сървъра“ прегледен, докато Аделина не
поеме (евентуално, изрично) привилегировани права.
